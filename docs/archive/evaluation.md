# 学习计划评估

> ⚠️ **历史文档**：针对早期/v2 周数计划的评估，不是当前进度。现状见根目录 `HANDOFF.md`。

## 总体判断

计划的方向正确，阶段划分合理，但存在**范围过大、深度不足、缺少动手环节**三个核心问题。19周内覆盖从Spring Boot基础到多租户生产系统，对"零后端经验"的前端开发者来说偏激进。

---

## 逐阶段评估

### 第1周：工程化细节补课 ✅ 方向对，时间偏紧

- "3-5天就够"过于乐观。自学者对分层设计、事务边界的理解往往停留在"知道概念"，真正审查出问题需要有人指导或大量试错。
- **建议**：延长到1.5-2周，加入实际跑测试、故意制造异常看行为的练习，而不只是"问大模型review"。

### 第2-3周：LLM API基础 ⚠️ 内容密度高

- OkHttp调用 + SSE解析 + Token计费，三件事放两周对新手偏紧。
- SSE解析是难点（chunk边界、event类型、错误处理），单独一周都不为过。
- **建议**：第2周只做普通HTTP调用+响应解析，第3周专注SSE流式。Token计费可以穿插了解，不需单独列任务。

### 第4周：Tool Use ✅ 合理

- 一周够理解JSON Schema + 实现单轮工具调用。
- "多轮Agent Loop"放在这里可能有点赶，但作为验收标准要求可以接受。

### 第5-7周：MCP协议 ⚠️ 最大风险区

- **Java MCP SDK成熟度存疑**。MCP生态以TypeScript/Python为主，Java SDK可能功能不全、文档不足、bug多。建议先调研再决定。
- "2026年事实标准"的表述有风险——MCP仍在快速演进，API可能变。
- 从stdio→Streamable HTTP的改造是好的学习路径。
- **建议**：第5周先用TypeScript/Python搭一个MCP Server理解协议，确认Java SDK可用后再迁移。不要在SDK不成熟时硬刚。

### 第8-10周：Java Agent框架 ⚠️ Redis前置知识缺失

- **Redis没有任何铺垫**。计划直接要求"历史存Redis"，但对Redis的数据结构、过期策略、持久化机制没有交代。
- Semantic Kernel Java版 vs LangGraph4j的选型，需要实际调研两者star数、文档质量、社区活跃度，不能只靠问大模型。
- Checkpoint机制"先用数据库实现"是好的决策。
- **建议**：在第8周开头加1-2天Redis基础（数据结构、过期策略、Spring Data Redis集成），或者明确说"需要先自学Redis基础"。

### 第11-12周：前端集成 ✅ 合理但架构需明确

- 对前端开发者来说这周最轻松，节奏可以快。
- 但**架构问题没交代**：前端直连LLM API还是通过后端代理？流式响应怎么转发？这些是关键设计决策。
- "可视化Agent执行链路"是个好需求，但Timeline组件只是展示，更重要的是数据结构设计（怎么序列化执行过程）。

### 第13-14周：MCP鉴权 ⚠️ OAuth 2.1复杂度被低估

- OAuth 2.1不是"两周能搞定"的东西。光是理解Authorization Server / Resource Server / Client三者关系就需要时间。
- Spring Security的OAuth2 Resource Server配置有大量坑（JWT验证、CORS、token刷新）。
- **建议**：如果只是MCP Server鉴权，可以先用简单的API Key方案验证链路通了，OAuth 2.1作为进阶内容。

### 第15-16周：可观测性 ⚠️ 前置知识多

- OpenTelemetry的span/trace概念需要分布式系统基础。
- "给Agent执行链路埋点"的前提是你已经有完整的Agent系统在运行。
- **建议**：如果Agent系统还没跑通，这阶段会空转。确保前面的模块已经整合。

### 第17-18周：成本控制与多租户 ❌ 范围过大

- **多租户是生产级系统设计**，涉及数据隔离、权限模型、资源配额，不是两周能搞定的。
- 令牌桶限流 + Token统计 + 多租户数据隔离，每一个单独拿出来都够学一周。
- **建议**：砍掉"多租户"，只做单用户的成本统计和限流。多租户作为"毕业后"的进阶内容。

---

## 整体结构性问题

### 1. "问大模型"的方式可以更高效

对零基础来说，问大模型是正确的学习方式，不用改。但可以加几个习惯让效果更好：
- 大模型给的代码**自己敲一遍**，不要复制粘贴。敲的过程中会发现哪里没理解。
- 遇到报错先读一遍错误信息，猜一下原因，再问大模型。不要直接丢报错问"怎么解决"。
- 每完成一个任务，用自己的话解释一遍"这段代码在干什么"，说不清楚说明没真懂。
- 大模型给的答案可能过时（Java SDK版本、API变化），跑不通是正常的，debug本身就是学习。

### 2. 缺少环境搭建和依赖管理

- 没有提到Docker（Redis、数据库需要）
- 没有提到Maven/Gradle依赖管理
- 没有提到IDE配置（IntelliJ IDEA推荐）
- 没有提到API Key获取和管理

### 3. 没有实际项目驱动

9个阶段都是"学概念→问大模型→验收"，没有一个贯穿始终的实际项目。建议：
- 选一个具体场景（比如"智能客服"或"代码审查助手"）
- 每个阶段的成果都往这个场景靠拢
- 最后自然整合成可演示的系统

### 4. 时间估算偏乐观

按目前计划，每周要完成2-3个任务，每个任务需要理解概念+写代码+调试。对"零后端经验"的开发者来说，很多任务实际需要的时间是计划的1.5-2倍。

---

## 建议修改

| 原计划 | 建议调整 |
|---|---|
| 第1周3-5天 | 延长到2周，加入实际测试 |
| 第2-3周LLM API | 拆成HTTP调用和SSE两个独立周 |
| 第5-7周MCP | 先用TS/Python验证，再迁移到Java |
| 第8-10周Agent框架 | 加Redis基础前置，或标注"需先自学" |
| 第13-14周OAuth 2.1 | 先用API Key，OAuth作为进阶 |
| 第17-18周多租户 | 砍掉多租户，只做单用户成本控制 |
| 全程"问大模型" | 保持，但加入"自己敲一遍+先猜原因再问"的习惯 |
| 无项目驱动 | 选一个实际场景贯穿始终 |

---

## 结论

计划的**阶段划分和学习路径是合理的**，问题在于范围过大（9个阶段覆盖了后端+Agent+前端+安全+监控+多租户）和深度不足（每个都只是"了解"而非"掌握"）。

建议：**砍掉第7-9阶段（鉴权、可观测性、多租户）**，把省下的时间分给前6个阶段加深理解。这些生产级内容可以等基础打牢后再学。19周打牢Agent开发核心能力（LLM API + Tool Use + MCP + Agent框架 + 前端集成）已经很充实了。
